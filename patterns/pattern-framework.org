#+title: The ELOT pattern framework
#+subtitle: Rules for writing and applying ELOT patterns
#+author: johanw
#+date: 2026
#+call: theme-elot()

This file defines the common rules for ELOT patterns. See
[[file:README.org][README.org]] for the pattern index and short application checklist. See
[[file:pattern-vocabulary.org][pattern-vocabulary.org]] for the annotation properties.

* Pattern structure

One pattern is one ELOT file and one ontology. The ontology IRI identifies the
pattern.

A pattern contains two kinds of resource:

- A constant has an external CURIE and is used unchanged in every application.
- A placeholder has a =var:= CURIE and is replaced when the pattern is applied.

Each pattern must contain:

1. A prefix table and ontology declaration.
2. An import of =pattern:pattern-vocabulary= and imports of the ontologies whose
   terms it uses.
3. A /How to apply/ section.
4. A /Required constants/ section.
5. A worked example with a substitution table.
6. A warning section that states the main limit or reason not to use the
   pattern.
7. Constants and placeholders with =pattern:action= annotations.
8. A clean lint, OWL parse, and consistency result with imports loaded.

Manchester Syntax requires every used resource to be declared in the file.
Imports do not remove this requirement. Declare every external term and every
used =pattern:= annotation property locally.

* Actions

=pattern:action= tells the user what to do with a resource:

- =BORROW=: use the external resource named by the pattern constant.
- =BIND=: use a resource already declared in the target.
- =MINT=: create a new target resource.
- =BORROW_OR_MINT=: look for a suitable external resource; mint one if none
  exists.
- =BIND_OR_MINT=: prefer an existing target resource; mint only when needed.
- =MINT_OR_BIND=: normally mint, but allow an existing target resource.

The order in a combined action states the preferred choice.

=pattern:instruction= gives any further rule for the resource. It should state
its expected kind, when reuse is valid, and any naming or placement rule.

These annotations guide application. They do not affect OWL reasoning. Remove
them from instantiated target resources.

* Constants and provenance

A pattern constant fixes the resource identity. Its declaration must include:

- the exact CURIE;
- the correct OWL kind;
- its =rdfs:isDefinedBy= value;
- =pattern:action :: BORROW=.

When copying a constant to a target:

1. Read the constant declaration from the pattern.
2. Resolve any prefixes using the pattern's prefix table.
3. Call =elot_declare_resource= with the exact CURIE, label, and kind.
4. Pass the pattern's =rdfs:isDefinedBy= value as =defined_by=.
5. Set =borrow=false=.

This writes the declaration and provenance in one edit. It does not consult the
ELOT database. The pattern author is responsible for the =rdfs:isDefinedBy=
value. The value may be a CURIE, an IRI, or another value accepted by ELOT.

Do not use =borrow=true= for a constant copied from a pattern. That option asks
the database to choose provenance and may select a different ontology version.

Use the database when identity or provenance is not already fixed. This is
common for =BORROW_OR_MINT= slots, such as a unit or quantity kind. Label search
is suitable for finding candidates. After selection, use exact identity and
kind.

* Constant placement

Do not copy the complete source hierarchy by default.

For a constant with a parent in the pattern:

1. If the parent is also required by the selected pattern part, declare the
   parent first and place the child below it.
2. If the parent already exists in the target with the right identity and kind,
   place the child below it.
3. Otherwise place the child at the root of its resource section.

Do not add a parent only to reproduce the source outline. If a resource has
more than one required parent, use one for heading placement and write the
others as explicit =SubClassOf= or =SubPropertyOf= rows.

* Placeholders and literals

Replace every =var:= resource in the selected part of a pattern. The replacement
must have the expected OWL kind.

A literal placeholder is marked by a nested =pattern:value= row:

#+begin_example
 - Facts :: lis:datumValue "100"^^xsd:decimal
   - pattern:value :: xsd:decimal
#+end_example

Replace the example literal with a real value of the stated datatype. Remove
the =pattern:value= annotation from the result.

Shared classes and properties should normally be reused in later applications.
Situation-specific individuals should normally be minted for each application.
The action and instruction on each placeholder decide the case.

* Optional and repeated parts

A pattern with independent parts must explain how to select them.

Before editing:

1. Mark each part selected or unselected.
2. State the evidence for every selected part.
3. Fill slots only for selected parts.
4. Keep every selected part complete.
5. Omit every unselected part completely.

There is no pressure to select every available part. Do not invent data to
complete a part.

For repeated parts, record one set of bindings for each repetition. Reuse a
shared anchor when the pattern says it may be bound.

* Application procedure

1. Read the pattern's application, selection, constants, example, and warning
   sections.
2. Inspect the target ontology.
3. Select the applicable pattern parts.
4. Make a binding table for every selected placeholder and literal.
5. Add required constants with =elot_declare_resource=, =defined_by=, and
   =borrow=false=.
6. Reuse or mint target resources according to each action.
7. Check proposed axiom rows before committing them.
8. Reproduce the selected pattern axioms with the chosen substitutions.
9. Remove =pattern:action=, =pattern:instruction=, =pattern:value=, and other
   template-only annotations.
10. Add =pattern:appliedPattern= where the pattern directs.
11. Run =elot_check= and any pattern-specific query.

Stop instead of guessing when:

- required information is missing;
- a resource identity is unclear;
- the OWL kind is wrong;
- a required slot cannot be filled;
- a proposed row fails validation;
- the pattern's warning applies.

The current ELOT tools edit declarations and axiom rows. They do not apply a
whole pattern in one transaction. Use small related edits and dry runs when
available.

* Authoring a pattern

1. Choose a recurring ontology structure, not a change of label or example.
2. Check whether an existing pattern already provides the same structure.
3. Inspect the source ontology and verify every external resource, property
   direction, kind, parent, domain, range, inverse, and restriction used.
4. Add the real source ontology and its import closure to =patterns/=. Do not
   replace it with a small hand-written file.
5. Add missing import mappings to =catalog-v001.xml=.
6. Create one pattern file with a stable ontology IRI and version information.
7. Mark external constants with =BORROW= and =rdfs:isDefinedBy=.
8. Mark placeholders with the narrowest suitable action and a clear
   instruction.
9. Write the smallest axiom set that expresses the intended structure.
10. State whether inverse facts are asserted or only inferred.
11. Add application, constants, example, and warning sections.
12. Run the library checks with imports loaded.
13. Apply the pattern once to a real target and inspect the result.
14. Add the pattern to the README index.

Use =elot_db_activate_source= and the database inspection tools while designing
a pattern when they help verify the source vocabulary. Database discovery is
not required when applying a constant whose identity and provenance are already
written in the pattern.

* Imports and the catalog

Each =Import ::= value is an ontology IRI. =catalog-v001.xml= maps that IRI to a
local ontology file. Local ELOT dependencies map to their tangled files, not to
their Org sources.

When adding a pattern:

- add a catalog entry for every imported ontology not already mapped;
- include all transitive imports needed for checking;
- add a catalog entry when one pattern imports another;
- keep downloaded ontologies unchanged;
- update =patterns/Makefile= when a source needs a repeatable download or
  conversion step.

Run:

#+begin_example
make -C patterns vendor check
make -C patterns elot-check FILES="My-pattern.org"
#+end_example

A successful check must include OWL parsing and a consistency result. A report
where ROBOT stages are skipped is not full validation.

* Common modelling rules

- Assert both directions of a relation when the pattern requires easy querying
  without inference.
- Preserve a selected pattern's axiom directions and restrictions.
- Keep independent restrictions in separate rows so they can be edited and
  checked separately.
- Do not add local logical axioms to an imported resource unless the pattern or
  target requires them and their effect has been checked.
- Do not copy definitions from an imported ontology unless a local copy is
  explicitly needed.

* Application record

=pattern:appliedPattern= records which pattern was used. The best attachment
point is still under review. Follow the rule stated by the selected pattern.
Do not annotate unrelated resources merely because they were already present in
the target.

* Open work

The following points are not settled:

1. The standard attachment point for =pattern:appliedPattern=.
2. Whether application records should use a versioned pattern IRI.
3. A single tool that plans and applies a complete pattern.
4. Structured support for complex conditions and repeated groups.
5. A permanent namespace for the experimental =pattern:= vocabulary.
