This directory contains ELOT pattern files. Each pattern is an ontology and an
executable template.

* Apply a pattern

1. Read the pattern's /How to apply/ section, leg-selection rules, required
   constants, worked example, and warning section.
2. Inspect the target ontology. Decide which existing resources to reuse and
   which selected slots need new resources. Do not invent missing source data.
3. Add each required pattern constant to the target by exact CURIE, label, and
   kind. Copy its =rdfs:isDefinedBy= value from the pattern:
   - resolve the value with the pattern's prefix table when needed;
   - call =elot_declare_resource= with =borrow=false= and =defined_by= set to
     that value;
   - do not use the database to rediscover a constant already fixed by the
     pattern.
4. Preserve only useful local hierarchy:
   - if the constant's pattern parent is also required, declare the parent
     first and place the child below it;
   - if that parent already exists in the target, place the child below it;
   - otherwise place the constant at the root of its resource section;
   - do not add an unused chain of source parents.
5. Use the ELOT database only when a resource must be discovered, such as a
   =BORROW_OR_MINT= slot. A label search may find candidates, but select the
   final resource by identity and kind.
6. Resolve any leg-selection step. Bind or mint every =var:= slot in each
   selected leg. Keep a selected leg complete and omit each unselected leg.
7. Reproduce the selected axioms, remove template annotations, add
   =pattern:appliedPattern= where the pattern requires it, and run
   =elot_check=.

For a constant copied from a pattern, use =defined_by=. Do not use
=borrow=true=: that asks the database to choose provenance.

See [[file:pattern-framework.org][pattern-framework.org]] for the full rules and
[[file:pattern-vocabulary.org][pattern-vocabulary.org]] for the annotation
properties.

Run library checks with =make test=. Set =ELOT_REQUIRE_ROBOT=1= to require
ROBOT-backed checks.

* Pattern index

Choose a pattern before filling its placeholders.

#+caption: Patterns in this library
| pattern                              | detail level   | individuals introduced       | choose it when                                                                                                            |
|--------------------------------------+----------------+------------------------------+---------------------------------------------------------------------------------------------------------------------------|
| IDO-pattern-quantity-datum-fullform  | full           | quality, datum, unit         | the quality or datum must be referenced for sensing, provenance, qualifiers, or competing values                         |
| IDO-pattern-quantity-shortcut-object | reduced        | datum, unit                  | datum context is needed, but the quality is never referenced                                                              |
| IDO-pattern-quantity-shortcut-data   | minimal        | none                         | only the value is needed; the unit is known from the property convention                                                  |
| IDO-pattern-function                 | not applicable | function, activity           | what a thing is for, or the activity that realizes the function, must be stated                                           |
| IDO-pattern-participation            | generic roles  | activity                     | participants in an activity need agent and patient roles                                                                  |
| IDO-pattern-idef0                    | ICOM roles     | activity                     | participants need the IDEF0 Input, Control, Output, and Mechanism roles                                                    |
| SKOS-pattern-broader                 | not applicable | narrower concept             | a SKOS concept hierarchy is needed                                                                                        |
| PROV-O-pattern-qualified-activity    | qualified      | activity, usage, association | provenance must state what was used and generated, who acted, the plan, and the role                                     |
| IOF-pattern-information-about        | selectable legs | information content entities | information denotes, uniquely designates, describes, or prescribes an entity                                              |

The three quantity patterns keep different amounts of information. A reduced
form can be derived from a fuller form, but omitted individuals cannot be
recovered. Choose the fuller form when those individuals may need to be
referenced.

The participation and IDEF0 patterns use different role vocabularies. IDEF0's
relations are more specific. The function and participation patterns can be
combined: apply function first, then participation.

The IOF information-about pattern may use one or more legs. There is no
preference for using all four. Select only the legs supported by the available
information.

* Quantity values written in two forms

A reasoner will not compare a shortcut value with a full-form value unless the
ontology contains an explicit rule that connects them. If both forms are
allowed, use a rule or a query to check agreement. Otherwise require authors to
use only one form for each quality.

* Notes for pattern authors

- Use one file and one ontology for each pattern.
- Include the required prose sections and one worked substitution table.
- Give every constant its exact external CURIE, kind, and =rdfs:isDefinedBy=.
- Give every placeholder a clear action and instruction.
- State how optional or repeatable legs are selected.
- Test with the real imported ontologies, not small substitute files.
- Apply the pattern once to a real target before adding it to this index.
