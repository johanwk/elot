Pattern index and application entry point.

* Applying a pattern: mandatory checklist

1. Read *How to apply* and *Required constants (borrow these first)*.
2. For each =BORROW= constant, the first tool sequence is:
   1. =elot_db_activate_source= for the preferred source;
   2. =elot_borrow_term= with the constant's label and kind;
   3. =elot_db_supertypes=, then borrow and preserve its source parent.
3. On the first borrow attempt, *omit =lang=* and usually =source=; either
   filter can turn an existing term into a false “no candidates”. Narrow only
   to disambiguate, using the exact registered source string.
4. Do not call =elot_read_resource=, =elot_axiom_check=,
   =elot_db_search_label=, declaration, or mutation tools for that constant
   before step 2. Search manually only if =elot_borrow_term= returns multiple
   or no candidates.
5. Keep the borrow snippet's =rdfs:isDefinedBy= and definition. Never replace
   it with bare =elot_declare_resource=; declare only after borrow has failed,
   and add provenance explicitly.
6. Resolve any explicit leg-selection step. Then bind or mint every =var:=
   slot in the selected scope, reproduce each selected leg intact, prune whole
   unselected legs, remove template annotations, add =pattern:appliedPattern=,
   dry-run, and run =elot_check=.

*BORROW means borrow first, with provenance and source hierarchy; it never
means merely declaring an external CURIE.*

Run library checks with =make test=; set =ELOT_REQUIRE_ROBOT=1= to forbid
lint-only success.

See [[file:pattern-framework.org][pattern-framework.org]] for the contract and procedure, and
[[file:pattern-vocabulary.org][pattern-vocabulary.org]] for the annotation vocabulary.

* Cross-pattern index

Choose a pattern before filling in its placeholders.

#+caption: Patterns in this library
| pattern                              | fidelity       | individuals introduced       | when to choose                                                                                                            |
|--------------------------------------+----------------+------------------------------+---------------------------------------------------------------------------------------------------------------------------|
| IDO-pattern-quantity-datum-fullform  | full (verbose) | quality, datum, unit         | the quality or the datum must itself be referenced -- sensor, measuring activity, provenance, qualifier, competing values |
| IDO-pattern-quantity-shortcut-object | reduced        | datum, unit                  | datum-level context wanted (unit as a resource, qualifier, provenance) but the quality is never referenced                |
| IDO-pattern-quantity-shortcut-data   | minimal        | none                         | value only; one triple per quantity, smallest graph, most reasoner-friendly; unit recoverable only by property convention |
| IDO-pattern-function                 | n/a (see note) | function, activity           | what a thing is *for* must be stated, and/or the activity realizing it must be referenced                                   |
| IDO-pattern-participation            | generic roles  | activity                     | an activity's cast must be recorded with agent/patient roles distinguished                                                |
| IDO-pattern-idef0                    | ICOM roles     | activity                     | the same cast, in IDEF0's four roles: Input, Control, Output, Mechanism -- systems-engineering workflows                  |
| SKOS-pattern-broader                 | n/a (see note) | narrower concept             | establishing a taxonomic hierarchy between SKOS concepts via outline nesting                                              |
| PROV-O-pattern-qualified-activity    | qualified      | activity, usage, association | provenance: what an activity used and generated, who ran it, under what plan -- with the role reified, not name-encoded   |
| IOF-pattern-information-about        | aboutness modes | information content entities | information denotes, uniquely designates, describes, or prescribes an entity                                               |

The /fidelity/ column compares a pattern with its own variants.  The
three quantity patterns differ in how much detail they keep.
Participation and idef0 differ instead in which role vocabulary they
use: idef0's four ICOM relations are sub-properties of the relations
participation uses, so an idef0 instantiation entails the participation
one, but not the other way round.  The remaining patterns have no
variants and read =n/a=.

Function and participation are not variants but compose: the activity
that realizes a function is the kind of activity whose participants the
participation (or idef0) pattern describes.  Apply function first, then
participation.

=SKOS-pattern-broader= and =PROV-O-pattern-qualified-activity= are
written for ontologies other than IDO, and use the =pattern:=
vocabulary, the =var:= convention and the prose blocks unchanged.  The
only extra step was adding =skos.ttl= and =prov.ttl= to the catalog;
both are verbatim upstream copies fetched by =patterns/Makefile= (see
the provisioning rule in [[file:pattern-framework.org][pattern-framework.org]]).

=IDO-pattern-idef0= cannot say that one thing plays different roles in
one activity; =PROV-O-pattern-qualified-activity= can, using
=prov:Usage= and =prov:hadRole=.  Whether the framework should
prescribe reified roles is open question 6 in
[[file:pattern-framework.org][pattern-framework.org]].

** Choosing among the patterns

The three quantification patterns are not mutually exclusive: one
ontology may use all three, for different qualities.  The choice is
made per quality, not per ontology.

The index rows are ordered by decreasing detail; each step down omits
resources, and with them the questions that can be answered.  A query
can derive a shortcut form from a full-form instantiation, but not the
reverse, since that would mean creating the omitted individual.  When
in doubt, choose the more explicit pattern.

* Shortcut values and full-form values do not check each other

If the same quality of the same thing is written down twice -- once
with a shortcut pattern (a single number) and once with the full-form
pattern -- the reasoner will not report a mismatch between the two
numbers.  They are two unconnected statements, and nothing in the
patterns says they must agree.  Making the connecting relation
functional does not help: it forces the two descriptions to be about
the same shaft, not about the same length.

This is a data-quality question, not a logical contradiction, so
=elot_consistency= is not the tool for it.  Choose one of:

1. a rule language such as SWRL, to require the numbers to be equal;
2. an authoring rule that a given quality is recorded either the
   shortcut way or the full way, never both;
3. a query, run separately, that lists things having both a shortcut
   and a full-form value and compares them.

* Findings from writing the library

- The template contract held for every pattern written so far,
  including patterns about dispositions and events rather than
  attributes.  No new keyword and no exception was needed.
- The fourth prose block is not only /Relationship to <sibling>/: the
  contract is three mandatory blocks plus one that discusses the
  pattern's own main difficulty, of which the sibling block is one
  case.
- The share of TBox and ABox slots varies widely between patterns.  The
  quantity patterns are mostly TBox; the function pattern has one
  bind-first slot and is otherwise ABox.
- A pattern that asserts a fact and also falls under an upper-ontology
  chain axiom entailing a weaker version of it should say so, and treat
  the difference as a data-quality question (see the previous section).
- Repeating a pattern against a bound anchor covers the simple cases of
  variable cardinality, so a pattern with a repeatable leg should mark
  its anchor slot =MINT_OR_BIND=, not =MINT=.
- A check for borrowed terms that do not exist in the named source was
  considered and not implemented: =rdfs:isDefinedBy= often names a
  namespace rather than an ontology, and sources are often ingested
  under a different base IRI or from a subset, so the check would give
  many false warnings.  Borrowed terms remain a matter for review.
