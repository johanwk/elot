#+AUTHOR: ELOT Contributors
#+STARTUP: overview

* Purpose of this document

This is the *single, authoritative* plan for finishing =elot-gptel=
and shipping it as part of a new ELOT MELPA release.  It replaces the
sprawling =ELOT-GPTEL-PLAN.org=, which has been retired and archived
(moved out of the git root -- see "Relationship to the old plan"
below).  This document stands on its own; the archived plan is not
required reading.

The goal is deliberately narrow and conservative:

#+begin_quote
Take the =elot-gptel-0.1= branch from its /current/ state to a state
where it can be merged into =main= with confidence, then tagged for a
new ELOT MELPA package release.
#+end_quote

We are *not* adding new capability surface.  The tool set that exists
today (diagnostics, DB, identifier minting, authoring/mutation tools)
*is* v1.  Everything here is stabilisation, hardening, documentation,
and packaging.  New feature milestones are explicitly *deferred to
post-v1* (see "Deferred to post-v1").

** Guiding principles

1. *Freeze the surface.*  No new tools, no new args, no new schemes
   land before v1.  A bug fix that changes a tool's /output shape/
   is allowed only if a test pins the new shape.
2. *One concern per step.*  Each step below is independently
   reviewable and independently revertible.
3. *Green before proceed.*  A step is DONE only when its acceptance
   check passes and the full test suite is still green.
4. *Prefer deletion over addition.*  If a half-built feature adds
   risk, disable/hide it for v1 rather than finish it.
5. *Cautious defaults.*  Side effects stay off by default; the
   read-only surface is the promise we make to first-time users.

* Phase 1.5 -- Structural refactor of the tool-spec table

Not a correctness fix, but a *risk-reduction* step that should land
before further work builds on the spec table.  The problem: the whole
tool surface (37 tools) is declared as *one* 1734-line quasi-quoted
=defconst elot-gptel--tool-specs= (=elot-gptel.el= ~l.6797).  A single
misplaced paren, stray unquote-=,=, or unbalanced =[...]= deep inside
that literal breaks the entire =defconst=, and the reader error
surfaces far from its cause.  The current shape is not acceptable even
for v1.

The registry meta-test (Step 1.2) is the safety net: the assembled
=elot-gptel--tool-specs= value must stay *behaviourally identical*
(same tools, args, arities, =:confirm= flags) across this refactor, so
=make gptel-registry-test= (plus =make byte-compile=) proves no
regression.  This is a pure refactor -- no tool behaviour changes.

*Call-site sizing (from a Step-1.5 scoping scan of =elot-gptel.el=):*

- =:name= arg-plist entries total ~136 across the 37 specs.
- The most-repeated args by name: =file= x24, =source= x8, =subject= x5,
  =content= x4, =format= x4, =limit= x4, =reasoner= x4, =dry_run= x4,
  plus =kind= / =lang= / =op= / =anchor= / =labels= recurring across the
  insert and DB families.
- The =file= description string "Path to an ELOT .org file, relative to
  the project root." is byte-identical in 7 places; =dry_run= carries
  near-identical boolean-plus-restore prose in its 4 sites.  These are
  latent divergence bugs (the wordings can silently drift apart) as
  well as line bloat.
- The same idea is already expressed *two ways* in the current source:
  "Path to an ELOT .org file, relative to the project root." vs the
  shorter variant "Path to an ELOT .org file (project-relative)."
  These must be harmonised to a single canonical wording *before* the
  split (see Step 1.5.0), otherwise the factored-out fragment
  (Step 1.5.2) would silently pick one and quietly change the other
  tool's schema.

*Shallow assessment of other size levers in =elot-gptel.el= (384 KB,
~9000 lines), recorded so they are not lost -- NOT in scope here:*

- The file is a flat single module: 37 tool implementations + the spec
  table + registration in one =.el=.  A later split into topical files
  (=elot-gptel-read.el= / =-db.el= / =-mutate.el= / =-robot.el=
  wrappers + a thin =elot-gptel.el= that requires them and registers)
  is the bigger structural win, but it is riskier and out of scope for
  v1.  Logged as a post-v1 candidate.
- Several long =:description= docstrings (30-60 lines each) dominate the
  byte count.  Externalising them (as =elot-conventions.md= already is)
  is possible but adds indirection and an ASCII/JSON-boundary concern;
  deliberately NOT pursued now.
- Do NOT introduce a spec-building =defmacro=: it would hide the
  structure the meta-test relies on and make paren errors harder, not
  easier, to localise.  Specs stay inert data.

** DONE Step 1.5.0 Harmonise duplicated arg descriptions

Before any structural change, converge the arg =:description= strings
that mean the same thing onto a *single* canonical wording, so the
later fragment extraction (Step 1.5.2) is a pure lift with nothing to
choose between.  Known divergences to reconcile:

- =file=: "Path to an ELOT .org file, relative to the project root."
  vs "Path to an ELOT .org file (project-relative)." -> pick one
  canonical form and apply it to every =file= arg.
- Sweep the other recurring args (=source=, =dry_run=, =reasoner=,

This is a text-only change to =:description= strings; no arg names,
types, enums, or =:optional= flags change, so the tool schemas are
externally unchanged.

*Acceptance:* =make gptel-registry-test= green; a grep shows each
harmonised arg description appears in exactly one canonical form (no
surviving variants); assembled =elot-gptel--tool-specs= differs from
the pre-change value only in =:description= text.

** DONE Step 1.5.2 Factor out shared arg fragments

Define the recurring arg plists once (=elot-gptel--arg-file=,
=elot-gptel--arg-content=, =elot-gptel--arg-dry-run=,
=elot-gptel--arg-reasoner=, =elot-gptel--arg-format=,

**** Scrutiny of =elot_replace_with_parent= (the novel tool)

The tool enumerates SUBJECT's immediate parents (heading-nesting
resource parent + bare-CURIE =SubClassOf= / =SubPropertyOf= rows,
class expressions conservatively rejected), then delegates to
=elot_rename_resource= with =op=merge= (SOURCE=SUBJECT,
TARGET=chosen parent).  The guard is clean and well tested.  Three
substantive weaknesses surfaced:

1. *The "safe semantic weakening" claim is only true for covariant
   occurrences.*  The docstring asserts "anything previously asserted
   as SUBJECT is still true under PARENT, by the SubClassOf
   semantics."  That holds for positive/covariant positions
   (=a ex:subject=, =SubClassOf :: ex:subject=, domain/range, the
   filler of a =some= restriction).  It does NOT hold in
   *contravariant* positions: =SubClassOf :: not ex:subject= becomes
   =not ex:parent= (a *strengthening*, since =not parent= ⊑
   =not subject=), and =only ex:subject= / left-hand-side and
   complement positions flip likewise.  Because =op=merge= rewrites
   *every* occurrence globally (the parent-enumeration conservatism
   does NOT narrow the rewrite scope), a fold can strengthen or even
   make the ontology inconsistent in a way the tool's own prose
   promises it won't.

2. *Post-fold revalidation is lint + OMN-parse only -- no reasoner
   consistency check.*  The inherited =elot-gptel--rename-revalidate=
   pipeline runs =elot_lint= (+ =elot_omn_validate= when ROBOT is
   present) but NOT =elot_consistency= / =elot_unsatisfiable=.  So an
   inconsistency introduced via weakness (1) commits and passes
   revalidation; only a later, separate reasoner run would catch it.

3. *=dry_run= is a real-write-then-restore, not a pure in-memory dry
   run.*  Unlike =elot_edit_axioms= (which validates an in-memory
   draft and never saves), the replace-with-parent =dry_run= path
   forces =allow-side-effects=t=, actually runs the merge (which
   =save-buffer='s to disk), then restores disk+buffer in an
   =unwind-protect=.  The restore is careful (modtime realignment to
   dodge supersession-threat prompts, lockfile suppression), but a
   crash between the inner save and the restore leaves the file
   mutated.  Narrow, but a real durability edge the other dry-run
   tools do not have.

None of these is a correctness bug in the tested paths; they are
contract-accuracy and defence-in-depth gaps.  Verdict: *ship, with
the covariance caveat documented and (1)/(2) tracked* -- see
decisions.

**** Justified false positive: =error= / =user-error= in =condition-case= handler position

Melpazoid/checkdoc flags 63 sites in =elot-gptel.el= with:

: No `format' required; `error'/`user-error' takes an f-string

*All 63 are false positives and must NOT be "fixed".*  Each is a
=condition-case= /handler clause/, not a call:

#+begin_src elisp
(condition-case err
    ...body...
  (user-error (format "ERROR: %s" (error-message-string err)))
  (error      (format "ERROR: %s" (error-message-string err))))
#+end_src

Here the =car= (=error= / =user-error=) is the /condition name/ being
caught; the rest is the handler /body/, whose value is *returned*.  The
=(format "ERROR: %s" ...)= builds the =ERROR:=-prefixed string that the
tool returns to gptel (the uniform failure envelope from Step 1.3).
The checkdoc heuristic only sees the textual pattern =(error (format
...))= and cannot tell that =error= is in condition-name position, not
call position.

Removing =format= here is an *active regression*: the handler body
becomes two forms (the format string discarded, the bare message
returned), stripping the =ERROR:= prefix.  This exact edit broke
=elot-gptel-axiom-check-test-empty-fragment= and
=...-unknown-subject= during Step 4.1 vetting; it was reverted with
=git restore=.

Classification of the 63 hits (line numbers per the melpazoid run):
- 31 =error= + 32 =user-error= entries; the flagged lines come in
  mirrored =user-error= /N/ + =error= /N+1/ pairs at identical
  indentation (577/579, 871/872, 1056/1057, ...), all with body
  =(format "ERROR: %s" (error-message-string err))=.
- The two unpaired entries (single-condition handlers) were inspected
  individually and are likewise handler clauses.
- *Verdict: zero real calls, 63 handler clauses.  Retain =format= in
  all.*  This is a documented, justified class of checkdoc noise to
  ignore, not silence in-code.

/Triage rule for future edits./ The =(error (format ...))= ->
=(error "..." ...)= rewrite is valid *only* where =error= /
=user-error= are genuinely /called/.  When they appear as the =car= of
a =condition-case= / =handler-case= clause they are condition names --
keep the =format=.

- *Minted-CURIE forward-reference in batch edits* (confirmed live
  friction; see =briefings/ELOT-REGULATION-ONTOLOGY-DESIGN.org=,
  "Minted-CURIE forward-reference").  A term minted via
  =elot_insert_*= / =elot_mint_identifier= cannot be referenced as an
  axiom *subject* in the same conceptual step, because the slurp
  signature used by =elot_edit_axiom(s)= for subject resolution does
  not yet include the new CURIE -- the batch fails atomically with
  =subject ... not found=.  Preferred post-v1 fix (per the design
  doc): let =elot_edit_axioms= accept a synthetic
  =subject=$introduced[K]= reference resolving to the CURIE minted by
  edit K, so a batch can mint + axiomatise in one atomic group.
  Alternative: a composite =elot_mint_and_axiomatise= tool.  Neither
  ships in v1.  *Documented v1 workarounds* (carry these into the
  Step 3.1 user docs):
  1. /Two-call sequence/: insert/mint first, read the minted CURIE
     from the =OK:= envelope (=Minted CURIEs:= list), then issue the
     axiom batch in a second =elot_edit_axioms= call using that exact
     CURIE as =subject=.
  2. /Re-issue on failure/: if a batch fails with =subject ... not
     found= for a just-minted term, re-issue the same batch with the
     minted CURIE substituted -- the failure is atomic, so the file
     is untouched and the retry is safe.
  3. /Order-independent rows first/: where possible, attach axioms to
     the new term via rows on *already-declared* subjects (e.g. add
     the =SubClassOf= via heading nesting at insert time) so no
     same-batch forward reference is needed.
- *=uuid= identifier scheme mints XML-unsafe (leading-digit)
  local-names* (confirmed live friction, 2026-07).  =elot-id--uuid-mint=
  emits =(downcase (org-id-uuid))= with no alpha lead-in, so ~⅝ of
  minted UUIDs begin with a hex digit.  A bare-digit-leading local part
  is a valid Turtle =PN_LOCAL= but *not* a valid XML =NCName=, so it is
  rejected by the RDF/XML and OWL/XML serialisations that ROBOT / the
  OWLAPI use heavily (a leading digit is illegal for an =NCName= first
  char).  This is why OBO IDs are =GO_0008150=, and why the LLM
  spontaneously prepended =C_= when asked to mint UUID-style IDs in
  =examples/pets.org= -- the workaround is correct, but the scheme
  *default* should not require it.  The verify side compounds it:
  =elot-id--uuid-localname-regexp= requires the bare =8-4-4-4-12= hex
  form and would *reject* a =C_=-prefixed identifier.  Preferred
  post-v1 fix: give the =uuid= scheme a configurable alpha lead-in
  (default a safe prefix such as =C_=, via =:scheme-params= like the
  acme =:slug= toggle already does) and widen the verify regexp to
  accept it, so every minted UUID is XML-safe by construction.
  Alternatives considered: keep raw UUIDs and document a Turtle-only
  caveat (leaves an RDF/XML footgun).  No v1 code change -- both Step
  3.3 (docstring/message-only) and Step 3.4 (packaging) are out of
  scope for a mint-behaviour change.
- *Windows CI* (deferred from Step 4.2, 2026-07).  The v1 merge gate
  runs GitHub Actions on Linux only (ubuntu-latest, Emacs 30.1).  A
  =windows-latest= matrix entry was considered and *dropped*: MSYS2 is
  the supported/tested Windows environment (it supplies the GNU
  coreutils, POSIX shell, and Unix-style paths the ROBOT wrapper,
  temp-file handling, and path resolution implicitly assume); a bare
  =windows-latest= runner has none of that, so a green job would not
  reflect real usage, and a red one would be a flaky gate the
  maintainer has no capacity to diagnose without a Linux-tool-equipped
  Windows box.  Path/line-ending regressions are better caught by
  OS-agnostic unit tests than by an OS matrix.  Post-v1: if Windows CI
  is revisited, base it on an MSYS2 environment, and note MSYS2 as the
  recommended Windows setup in the docs.

* Working discipline (how to run each step in gptel)

- Narrow to one step (=C-x n s=) before =gptel-send=.
- Read only what the step names; do not load the whole old plan.
- A step flips TODO -> DONE only after its acceptance check passes
  *and* the full suite is still green.
- Every code change is one reviewable, revertible commit with the
  step number in the message.
- When a step surfaces a scope question, stop and record a decision
  rather than expanding the step.
