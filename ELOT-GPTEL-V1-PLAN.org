#+TITLE: ELOT-gptel: Road to v1 (branch =elot-gptel-0.1= -> =main= -> MELPA)
#+AUTHOR: ELOT Contributors
#+STARTUP: overview

* Purpose of this document

This is the *single, authoritative* plan for finishing =elot-gptel=
and shipping it as part of a new ELOT MELPA release.  It replaces the
sprawling =ELOT-GPTEL-PLAN.org= (now retired -- see "Relationship to
the old plan" below).

The goal is deliberately narrow and conservative:

#+begin_quote
Take the =elot-gptel-0.1= branch from its /current/ state to a state
where it can be merged into =main= with confidence, then tagged for a
new ELOT MELPA package release.
#+end_quote

We are *not* adding new capability surface.  The tool set that exists
today (diagnostics, DB, identifier minting, authoring/mutation tools)
*is* v1.  Everything here is stabilisation, hardening, documentation,
and packaging.  New feature milestones are explicitly *deferred to
post-v1* (see "Deferred to post-v1").

** Guiding principles

1. *Freeze the surface.*  No new tools, no new args, no new schemes
   land before v1.  A bug fix that changes a tool's /output shape/
   is allowed only if a test pins the new shape.
2. *One concern per step.*  Each step below is independently
   reviewable and independently revertible.
3. *Green before proceed.*  A step is DONE only when its acceptance
   check passes and the full test suite is still green.
4. *Prefer deletion over addition.*  If a half-built feature adds
   risk, disable/hide it for v1 rather than finish it.
5. *Cautious defaults.*  Side effects stay off by default; the
   read-only surface is the promise we make to first-time users.

* Relationship to the old plan

=ELOT-GPTEL-PLAN.org= is *retired*.  Do not add new work items to it.
It remains in the repository only as a historical record of how the
tool surface was built (Milestones 1--10) and as the source of truth
for the /rationale/ behind individual tools.  When this v1 plan says
"the X tool", the authoritative description of X's behaviour is its
docstring + tool-spec in =elot-gptel.el=, with the old plan as
background.

What the old plan called Milestones 11--15 (fuzzy search, resource
move/rename ladder beyond what shipped, housekeeping lift,
=elot_new_ontology=, ROBOT impact analysis) is *out of scope for v1*.
See "Deferred to post-v1".

** TODO Step 0.4 Confirm the dependency posture

Verify (read-only) that:

- =gptel= is a *soft* dependency: =elot-gptel.el= loads and all

* Phase 1 -- Correctness hardening (make red green)

Fix only what Phase 0 surfaced.  No scope creep.

** TODO Step 1.1 Fix red tests

Turn every bucket-2 (red today) test green.  Each fix is its own
commit with the failing assertion quoted in the message.  If a test
is red because it encodes an /intended/ behaviour change that never
landed, either land the minimal fix or mark the test =ert-deftest=

*Acceptance:* all bucket-2 tests green; no test newly skipped without

** TODO Step 1.2 Dispatcher / spec consistency

Resolve any mismatch found in Step 0.1: every spec has a dispatcher
arm, every dispatcher arm has a spec, arities agree, enums in specs
match what the implementation validates.

Add a *meta-test* =test/elot-gptel-registry-test.el= that walks
=elot-gptel--tool-specs= and asserts, for each entry:
- =:function= is =fboundp=,
- a =elot-gptel--tool-thunk= arm exists (call it, expect no
  "no dispatcher" error),
- =:args= names are unique and non-empty,
- mutating specs (=:confirm=) dispatch to functions that honour the
  side-effects gate (smoke: call with the gate off, expect the
  refusal string).

*Acceptance:* the meta-test is green and would have caught the
Step 0.1 mismatches.

** TODO Step 1.3 Error-path uniformity audit

For every tool, confirm the failure contract:
- refusals and internal errors return a single =ERROR:= (or =FAIL:=)
  line, never signal out to gptel,
- traversal-guard refusal is uniform (=elot-gptel--resolve-file= /
  =--resolve-file-path=),
- ROBOT-absent refusal is uniform.

Where a tool is missing a =condition-case= wrapper or leaks a raw
=error-message-string=, add the wrapper.  Pin one refusal-shape test
per tool family (read-only, DB, mutating, ROBOT-backed).

*Acceptance:* a table (in the toolsheet) mapping each tool to its
verified error contract; representative tests green.

** TODO Step 1.4 Mutation-safety audit

Re-read =elot-gptel--apply-mutation= and each mutating tool against
the write-back contract:
- side-effects gate honoured (off => refuse without touching disk),
- =dry_run= (where offered) never writes and always restores the
  buffer,
- revalidation failure rolls the buffer back AND re-saves the
  pre-edit bytes,
- =elot-headline-hierarchy= is marked stale / refreshed post-write
  (9.3.F8 contract),
- =:confirm= behaviour matches =elot-gptel-confirm-mutations=.

Add/confirm a rollback test for at least: edit-axiom,
insert-sibling, rename, move, delete, replace-with-parent.

*Acceptance:* every mutating tool has a green rollback test and a
green gate-off refusal test.

* Phase 2 -- Scope decisions (decide what ships)

This phase makes explicit, recorded decisions about half-built or
risky surface.  Each decision goes in the Decisions Log.

** TODO Step 2.1 Confirm the v1 tool roster

Walk the toolsheet.  For each tool decide: *ship* / *hide* / *cut*.

- *ship*: stays registered, documented, tested.
- *hide*: implementation stays but it is removed from
  =elot-gptel--tool-specs= (so the LLM never sees it) -- use for
  anything not confidently robust.
- *cut*: delete implementation + tests (only if clearly dead).

Default bias for v1: when in doubt, *hide* rather than ship.  A
smaller, rock-solid roster is a better v1 than a large shaky one.

*Acceptance:* a "v1 roster" table in the Decisions Log with a
ship/hide/cut verdict and one-line rationale per tool.

** TODO Step 2.2 Confirm the resource move/rename/delete family status

The move/rename/delete/replace-with-parent tools are the highest-blast-radius
surface.  Decide per tool whether it is v1-ready or should be hidden:

- =elot_rename_resource= (incl. =merge= op)
- =elot_move_resource=
- =elot_delete_resource=
- =elot_replace_with_parent=
- the insert family

For each: confirm it has (a) a rollback test, (b) a dry-run test
where applicable, (c) a live acceptance check against a temp copy of
=examples/pets.org=.  Anything missing (b)/(c) is either completed
here or hidden for v1.

*Acceptance:* each tool in this family is either ship-with-full-tests
or hidden, recorded in the Decisions Log.

** TODO Step 2.3 Defaults review

Confirm the shipped defaults are the cautious ones:
- =elot-gptel-allow-side-effects= default nil,
- =elot-gptel-confirm-mutations= default =once-armed=,
- =elot-gptel-robot-catalog= default nil (auto-detect),
- content-size cap sane.

Document each default and its rationale in the user docs (Phase 3).

*Acceptance:* defaults table confirmed; no surprising default ships.

* Working discipline (how to run each step in gptel)

- Narrow to one step (=C-x n s=) before =gptel-send=.
- Read only what the step names; do not load the whole old plan.
- A step flips TODO -> DONE only after its acceptance check passes
  *and* the full suite is still green.
- Every code change is one reviewable, revertible commit with the
  step number in the message.
- When a step surfaces a scope question, stop and record a decision
  rather than expanding the step.
