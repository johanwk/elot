* About this ontology

This file describes the ELOT source repository itself: its files,
what depends on what, and what each file is for.  It is meant to help
someone working on ELOT's code understand how the package fits
together, and to let that understanding be checked by a reasoner
instead of just written down as prose.

** What it is useful for

- Working out what a change will affect.  The dependency links
  between modules are recorded here, so you can ask, for a given
  file, what depends on it (directly or through a chain of other
  files), or what it in turn depends on.
- Working out what a file is for.  Each module has a short statement
  of its purpose, and is linked to a function/activity it plays,
  so "what does this file do" can be answered by looking it up here
  rather than reading the file or guessing from its name.
- Checking test coverage.  Which files have a test, and which don't,
  is a plain query here.
- Catching things that were true once and are no longer true.  Since
  this is a checked model and not just a description, a wrong or
  outdated claim (for example, a dependency that no longer exists)
  can be caught by re-running a query or a consistency check, the
  way it can't be for an out-of-date paragraph in a text file.
- One example of this already happened: writing a competency
  question about external tools this package depends on showed that
  a real dependency (on the elot-exporter tool) was missing from the
  model.  Asking the question found a gap that nobody had noticed.

** What it is not trying to do

- It does not explain how to use ELOT.  It says nothing about
  commands, menu entries, settings, or how to write your first
  ontology file.  That is what the manual and the conventions
  document are for; this file only records that those documents
  exist, not what is in them.
- It is mainly useful to someone changing ELOT's code, not to someone
  just using it.  On a small codebase like this one, most of what it
  records could also be worked out by reading the files directly; the
  benefit grows as the codebase grows or as more people need to work
  on it without having read all of it.
- A different, separate model could describe ELOT from the user's
  side instead: the commands and menu entries a user sees, the
  settings they can change, and what each of the elot-gptel tools
  does.  That would be a genuinely useful thing to build, but it is a
  different job from the one this file does, and probably belongs in
  a separate file so that "how the code is put together" and "what a
  user can do with it" don't get mixed up in one place.

** Competency Questions: Package Maintainer Role

*** CQ1: Which Elisp modules are functional parts of the ELOT Emacs package source, and which are shipped in the MELPA artifact?

Method: SPARQL, checking each =lis:hasFunctionalPart= of the source
package (=ex:elot-package-2=) for whether it is also a
=lis:hasContentPart= of the MELPA build artifact
(=ex:elot-melpa-package=), using an =EXISTS= filter rather than a
join so modules present in the source but absent from MELPA (if any
existed) would show =false= rather than being silently dropped.

#+name: cq-modules-source-vs-melpa
#+begin_src sparql
  PREFIX ex: <http://example.org/resource/>
  PREFIX lis: <http://rds.posccaesar.org/ontology/lis14/rdl/>
  SELECT ?module (EXISTS { ex:elot-melpa-package lis:hasContentPart ?module } AS ?shippedInMelpa)
  {
    ex:elot-package-2 lis:hasFunctionalPart ?module .
  }
  ORDER BY ?module
#+end_src

Answer of record: all 16 Elisp modules that are functional parts of

*** CQ8: For each core module, what declared function does it have, and what activity class realizes that function?

Method: SPARQL for the module -> function -> function-class part
(=lis:hasFunction= joined to the function individual's asserted
=rdf:type=, excluding the =owl:NamedIndividual= marker).  The
*realizing activity* half needs a second query, because
=lis:realizedIn= is asserted as a class-level restriction on each
Function subclass (=SubClassOf lis:realizedIn only
ex:<activity-class>=), not as a per-individual =Facts= row: the
restriction has to be read off the OWL axiom (=owl:onProperty= /
=owl:allValuesFrom=) rather than a plain triple pattern.  A combined
query joins both halves in one table.

#+name: cq-module-function-and-class
#+begin_src sparql
  PREFIX ex: <http://example.org/resource/>
  PREFIX lis: <http://rds.posccaesar.org/ontology/lis14/rdl/>
  PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
  SELECT ?module ?function ?funcClass
  {
    ?module lis:hasFunction ?function .
    ?function rdf:type ?funcClass .
    FILTER(?funcClass != owl:NamedIndividual)
  }
  ORDER BY ?module
#+end_src

*** CQ9: Which artifacts are runtime payload (shipped in the MELPA package) versus authoring/test-only assets (tests, fixtures, tangle sources, docs)?

Method: SPARQL splitting all file-backed individuals (anything with an
=ex:repository-path=) into two groups by whether they are a content
part of =ex:elot-melpa-package=, using =FILTER (NOT) EXISTS=.

*** Elisp modules                                                :nodeclare:
**** On modelling the =require= graph as flat Facts               :nodeclare:
The =ex:requires-module= edges below are asserted as explicit =Facts=
rows on each module individual, rather than encoded through heading
nesting.  ELOT's =:ELOT-subheading-relation:= feature (used for
SKOS-style =skos:broader= trees, e.g. in =dnv-risk-taxonomy.org=) lets
outline nesting emit a relational =Fact= to the immediate parent --
but that machinery encodes exactly *one parent per node*, so it fits a
relation only when the underlying graph is a forest (a tree).

The intra-package =require= graph is emphatically *not* a forest:

- *Multiple parents in both directions.*  Most non-leaf modules
  =require= several others (=elot-gptel= -> 9, =elot-mode= -> 8,
  =elot= -> 7), and hub modules are =require='d by many (=elot-tangle=
  and =elot-db= are each pulled in by ~9 modules).  Because the
  fan-out is heavy in *both* orientations, neither =requires-module=
  nor a hypothetical inverse =required-by-module= reduces the graph to
  a tree -- inverting an edge only relocates the fan-out to a
  different node.
- *A genuine cycle.*  =elot-mode= requires =elot= and =elot= requires
  =elot-mode= (the latter via the soft =(require 'elot nil t)= form).
  No outline, in either orientation, can represent a cycle at all.

So "outliner thinking" buys us nothing here: any tree encoding would
have to drop most edges or duplicate module headings, breaking the
grounding discipline (one heading = one real file).  The flat,
per-type individual listing plus explicit =Facts= edges captures the
full multi-parent DAG (and the cycle) faithfully, while
=ex:depends-on= being =Transitive= still yields the reasoned
dependency closure for free.

***** Is this much internal coupling healthy?                  :nodeclare:
Offered as engineering commentary, not as asserted ontology:

- *A dense internal =require= web is common* for medium-to-large Elisp
  packages.  Emacs Lisp has no module or namespace system beyond
  features, so =require= is the *only* mechanism for load ordering and
  cross-file use; a package split across ~24 files will naturally
  accumulate many edges.  The count itself is unremarkable.
- *Hub modules are normal and largely healthy.*  A shared base
  (=elot-tangle=, =elot-db=) that many callers require is ordinary
  layering, not a smell -- it is exactly what you want if the base is
  cohesive and stable.
- *The one real wart is the cycle* =elot= <-> =elot-mode=.  Mutual
  =require= is a recognised Elisp anti-pattern; here it only loads
  because one side uses the soft, error-tolerant =(require 'elot nil
  t)=.  Such cycles usually indicate that a small shared core wants
  extracting into a third file that both sides can depend on
  one-directionally.  Worth flagging, not urgent -- and precisely the
  kind of finding a machine-checkable model of the package is good at
  surfacing.
